KTVHTTPCache 多范围响应数组越界崩溃修复记录

2025-10-22·性能优化与排查·Crash排查 / KTVHTTPCache / Runtime

修复KTVCocoaHTTPServer -[HTTPConnection continueSendingMultiRangeResponseBody]崩溃

KTVHTTPCache 崩溃修复总结

修复时间

2025/10/22

问题概述

崩溃信息

Fatal Exception: NSRangeException
*** -[__NSArrayM getObjects:range:]: range {2, 1} extends beyond bounds [0 .. 0]

调用栈：
0  CoreFoundation                 __exceptionPreprocess
1  libobjc.A.dylib                objc_exception_throw
2  CoreFoundation                 -[__NSArrayM getObjects:range:]  ← 崩溃点
3  KTVCocoaHTTPServer             -[HTTPConnection continueSendingMultiRangeResponseBody] + 1477
4  KTVCocoaHTTPServer             __43-[HTTPConnection responseHasAvailableData:]_block_invoke + 2528

问题分析

  • 崩溃原因：KTVHTTPCache 的 HTTP 多范围响应处理时，数组越界访问
  • 根本原因：continueSendingMultiRangeResponseBody 方法中调用 getObjects:range: 时，range 超出数组边界
  • 影响范围：使用 KTVHTTPCache 进行视频缓存播放的场景
  • 崩溃频率：中等频率，主要在网络环境不稳定时触发

问题定位过程

1. 依赖关系确认

Podfile（修改前）
  └─ pod 'KTVHTTPCache', '2.0.1'  ← 直接依赖
       └─ KTVCocoaHTTPServer (1.0.0)  ← 传递依赖（崩溃源）

Podfile（修改后）
  └─ pod 'KTVHTTPCache', '3.0.0'  ← 升级版本
       └─ KTVCocoaHTTPServer 代码已集成到 3.0.0 中（问题仍存在）

2. 现有防护检查

发现项目已有 NSMutableArray+AppRuntimeSafe 防护机制，但只 hook 了 objectAtIndex:，未覆盖 getObjects:range:：

// 现有防护（不足）
+ (void)hookRuntimeMethod {
    // 只 hook 了 objectAtIndex:
    [self safeSwizzleMethodWith:clsArrayM
                       oldSel:selObjectAtIndex
                       newSel:@"hookObjectAtIndex:"
                     toTarget:@"NSMutableArray"];
}

3. 崩溃点确认

通过调用栈分析，确定崩溃发生在：

// KTVCocoaHTTPServer/HTTPConnection.m:1477
- (void)continueSendingMultiRangeResponseBody {
    // ...
    [ranges getObjects:objects range:NSMakeRange(location, length)];  ← 崩溃
    // ...
}

解决方案： 方案一 + 方案二

方案一：升级 KTVHTTPCache 版本

  • 目标版本：2.0.1 → 3.0.0
  • 预期效果：修复已知 bug，优化 HTTP 多范围响应处理
  • 实际结果：升级后发现 3.0.0 版本集成了 KTVCocoaHTTPServer 代码，问题方法 continueSendingMultiRangeResponseBody 仍存在
  • 结论：版本升级无法彻底解决问题

方案二：添加数组越界防护（最终方案）

  • 核心策略：使用 Runtime Method Swizzling 技术，hook getObjects:range: 方法
  • 防护层级：在 Foundation 层面进行 hook，保护所有 NSMutableArray 调用
  • 混淆机制：使用项目现有的 CrashFixObfuscator 混淆框架，规避 App Store 审核
  • 兼容性：保持与现有 objectAtIndex: 防护的一致性

修改内容清单

CrashFixKey.swift（添加混淆 Key）

@objc public enum CrashFixSelKey: Int {
    case selObjectAtIndex
    case selObjectAtIndexedSubscript
    case selGetObjectsRange  //  新增
    
    var strValue: String {
        switch self {
        case .selObjectAtIndex:
            return "selObjectAtIndex"
        case .selObjectAtIndexedSubscript:
            return "selObjectAtIndexedSubscript"
        case .selGetObjectsRange:
            return "selGetObjectsRange"  //  新增
        }
    }
}

说明：

  • 添加 selGetObjectsRange 枚举值，用于混淆 getObjects:range: 方法名
  • 遵循项目私有API混淆规范，规避 App Store 审核

NSMutableArray+AppRuntimeSafe.m（实现 Hook）

Hook 注册

+ (void)hookRuntimeMethod {
    static dispatch_once_t onceToken;
    dispatch_once(&onceToken, ^{
        CrashFixObfuscator * hero = [CrashFixObfuscator share];
        NSString * clsArrayM = [hero getObfuscatedClassName: CrashFixClassKeyArrayM];
        
        // 现有：Hook objectAtIndex:
        NSString * selObjectAtIndex = [hero getObfuscatedSelName:CrashFixSelKeyObjectAtIndex];
        [self safeSwizzleMethodWith:clsArrayM
                           oldSel:selObjectAtIndex
                           newSel:@"hookObjectAtIndex:"
                         toTarget:@"NSMutableArray"];
        
        //  新增：Hook getObjects:range:
        NSString * selGetObjectsRange = [hero getObfuscatedSelName:CrashFixSelKeyGetObjectsRange];
        [self safeSwizzleMethodWith:clsArrayM
                           oldSel:selGetObjectsRange
                           newSel:@"hookGetObjects:range:"
                         toTarget:@"NSMutableArray"];
    });
}

Hook 实现

- (void)hookGetObjects:(id __unsafe_unretained [])objects range:(NSRange)range {
    // 检查 range 是否越界
    if (range.location + range.length > [self count]) {
        NSLog(@"[ArraySafeTest ObjC]  getObjects:range: 越界保护触发 - location:%lu + length:%lu > count:%lu", 
              (unsigned long)range.location, 
              (unsigned long)range.length, 
              (unsigned long)[self count]);
        return;  // 越界时直接返回，不执行原方法
    }
    
    // 没有越界，调用原方法
    [self hookGetObjects:objects range:range];
}

关键点：

  • 检查 range.location + range.length > count
  • 越界时直接 return，避免崩溃
  • 正常情况调用原方法（已交换后的实现）
  • 使用 __unsafe_unretained 修饰指针数组

selector_obfuscation_map（更新混淆映射）

更新前：300 字符（224 字节）
更新后：344 字符（256 字节）+44 字符

新增映射（加密后）：

{
  "selGetObjectsRange": "getObjects:range:"
}

编码验证：

  • 无换行符、无回车符、无空格
  • 标准 Base64 编码
  • 解码成功

    }

}

防护效果

完整防护矩阵

方法防护状态越界行为影响范围
`objectAtIndex:`已防护返回 nil直接调用
`getObjects:range:`已防护直接返回KTVHTTPCache 崩溃点
`removeObjectAtIndex:`间接保护通过 getObjects:range: 保护间接调用

崩溃场景模拟

原崩溃代码：

NSMutableArray *ranges = [NSMutableArray array];  // count = 0
[ranges getObjects:objects range:NSMakeRange(2, 1)];  //  崩溃

Hook 后行为：

- (void)hookGetObjects:(id __unsafe_unretained [])objects range:(NSRange)range {
    if (2 + 1 > 0) {  // 检测到越界
        NSLog(@" getObjects:range: 越界保护触发");
        return;  //  拦截，不崩溃
    }
    [self hookGetObjects:objects range:range];
}

结果： 崩溃被拦截，App 继续运行

技术要点

私有API混淆机制

为什么需要混淆？

  • App Store 会静态检测代码中是否使用私有API
  • 直接硬编码方法名（如 "getObjects:range:"）会被检测

混淆流程：

代码层（可见）
  CrashFixSelKey.selGetObjectsRange → "selGetObjectsRange"
         ↓
解密层（运行时）
  CrashFixObfuscator.getObfuscatedSelName() → 从 selector_obfuscation_map 解密
         ↓
Runtime Hook 层
  实际方法名："getObjects:range:"

优势：

  • 规避 App Store 静态检测
  • 防止逆向工程
  • 集中管理敏感API

注意事项

1. selector_obfuscation_map 文件管理

  • 文件已更新，包含新映射
  • 文件为加密格式，不要手动修改
  • 版本号保持 1.0（纯本地方案）

2. 防护生效条件

  • RemoteConfig.openFixArrayMCrash 开关需开启
  • App 启动时会自动加载 selector_obfuscation_map 并执行 Hook
  • 无需额外初始化

3. 性能影响

  • Hook 操作在 App 启动时一次性完成
  • 运行时性能影响极小（仅增加一次越界判断）
  • 只在越界时才输出日志

4. 兼容性

  • 适用于所有 iOS 版本
  • 不影响正常的数组操作
  • 与现有 objectAtIndex: 防护兼容

总结

问题根源

KTVHTTPCache 在处理 HTTP 多范围响应时，调用 getObjects:range: 方法发生数组越界，导致 NSRangeException 崩溃。

解决方案（两个层面）

1. 升级 KTVHTTPCache 依赖

  • 版本升级：2.0.1 → 3.0.0
  • 目的：修复第三方库已知 bug
  • 结果：问题方法仍存在，无法根治

2. 添加数组越界防护（核心方案）

  • 技术手段：Runtime Method Swizzling hook getObjects:range: 方法
  • 防护效果：越界时拦截并返回，避免崩溃
  • 防护范围：覆盖所有 NSMutableArray 的 getObjects:range: 调用

技术亮点

  1. 双重保障：依赖升级 + 防护兜底
  2. 使用私有API混淆机制，规避 App Store 审核
  3. 在 Foundation 层面进行防护，覆盖所有调用场景
  4. 完整的测试用例，可验证防护效果
  5. 性能影响极小，不影响正常功能
